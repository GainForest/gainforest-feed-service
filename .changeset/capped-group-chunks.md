Breaking change to the experimental activity feed: bursts and audio are capped at 200 rows per item, and audio is grouped by run instead of by upload day. Every page is now answered by one bounded statement.

- A burst or audio item covers at most 200 rows. A longer run is returned as consecutive chunk items, newest first. `total` counts the rows of that item only, not of the whole run.
- `burstItem` and `audioItem` gain `groupKey` (opaque; the same on every chunk of one run), `continued` (true on every chunk after the first) and `capped` (true when the chunk is full and the run goes on). Clients should merge a `continued` item into the card of the previous group item and show "200+" while the last chunk is `capped`. The single row left after a full chunk is still a group item, so `burstItem.total` can now be 1, when `continued` is true.
- Audio is no longer grouped by UTC day. An `audioItem` is a run of recordings that are adjacent in the feed, with the same owner and folder and no gap over 12 hours; any other selected row between two recordings ends the run, as for bursts. `audioItem.day` and `audioItem.createdAt` are removed and `from` and `to` are added. Uploads that interleave in time now make many short items.
- `groupKey` is stable only within one paging walk: it is derived from the run's newest record, so it changes when a newer record joins the run. A `capped` chunk is not guaranteed to be followed by a `continued` item when records change between two requests; `continued` is the authority.
- The cursor is version 2. It also names the run a page cut at 200 rows, by its `groupKey` and kind only, so the next page continues it without reading backwards. The run's account and folder are read from the cursor row in the database, so a cursor stays short whatever a record stores and a hand-made cursor cannot choose them. Cursors of version 1 are rejected with `InvalidCursor`; clients request the first page again.
- A cursor whose timestamp is a valid datetime that PostgreSQL cannot read (a day the month does not have such as `2026-02-30`, year 0000, or a UTC offset beyond ±15:59) now answers `InvalidCursor` (HTTP 400) instead of an internal error.
- `audioItem.did` is the account in the folder's AT-URI only when that is a valid DID; a handle or any other authority falls back to the recording's own account. `audioItem.deployment` is omitted when the recording's `deploymentRef` is not a valid AT-URI, so one malformed value no longer fails every page that holds the recording.
- A page runs one statement that reads at most `limit × 200 + 1` rows of the feed order. It reads only what it needs: it stops at the first row of the item after the one that shows a next page exists, so an ordinary page reads a few hundred rows. The scan windows, the repeated statements, and `ScanLimitExceeded` are removed from both procedures: a long run no longer fails a page, and a statement that exceeds the statement timeout is an `InternalError`.
- The statement no longer reads whole collections or sorts full records on a large page, and a viewer who follows nobody gets an empty page without reading any collection. No migration or index change is required.
- The database pool opens every session with `jit=off`, because the statement's estimated cost grows with the table and JIT compilation would add 100 to 150 ms to every page once it crosses the default threshold.
